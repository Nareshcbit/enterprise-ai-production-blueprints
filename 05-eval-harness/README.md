# Project 5: An Eval Harness You Can Ship On

A hands-on lab. You start with a naive eval harness for a claims-triage assistant and fix it one bug
at a time until a CI gate blocks bad prompts and lets good ones through.

It pairs with the Visual Walkthrough
[Build an Eval Harness You Can Ship On](https://nmadiraju.com/posts/genai-eval-harness/): the
walkthrough shows *why* each fix matters; this lab makes you write it. Every number on that page
(58%, 74%, 6 of 9, 74/79/71, ±9, 88%, 90%, 94%) comes out of this repo.

## The scenario

Northwind Insurance wants an assistant that triages claims as `urgent`, `standard` or `fast_track`.
Adjusters labelled 100 real claims. Claim **C-1042** is a burst pipe; the family is staying with a
neighbour tonight. The adjusters say `urgent`. Follow it through every step.

> **Synthetic data.** The claims, labels, calibration grades and recorded model outputs are generated by
> `tools/generate_synthetic.py`, shaped so the lab is free, offline and reproducible. Run `make live` to
> grade a real model on Amazon Bedrock; your numbers will differ.

## The steps

Work in order; later steps use earlier functions. Each fix step has one test file. Make it pass.

| Step | Kind | What you see or do | Command | You edit |
|---|---|---|---|---|
| A1 | how | One case, one recorded output | `make A1` | |
| A2 | bug | String match on free text says 58% | `make A2` | |
| A3 | fix | Parse structured output, grade the enum: 74% | `make A3` | `harness/graders.py` |
| B1 | bug | 74% overall hides 3 missed urgent claims | `make B1` | |
| B2 | fix | Confusion matrix and urgent recall (6 of 9) | `make B2` | `harness/metrics.py` |
| B3 | bug | Same prompt, three runs: 74%, 79%, 71% | `make B3` | |
| B4 | fix | Majority of 3, margin of error, paired diff, save the baseline | `make B4` | `harness/metrics.py` |
| C1 | bug | Exact match can't grade the reason text | `make C1` | |
| C2 | fix | LLM judge with a rubric, calibrated against adjusters: 88% | `make C2` | `harness/judge.py` |
| D1 | bug | Prompt v3: total rises to 90%, 4 cases quietly regress | `make D1` | |
| D2 | fix | CI gate: v3 exits 1, v4 exits 0 at 94% | `make D2` | `harness/gate.py` |

Stuck? `solutions/` has reference versions. `make check-solutions` runs every test against them in a
temporary copy, without touching your files.

## Live mode

`make live` and `make live-judge` call Amazon Bedrock. You need AWS credentials and access to the models
in your account. Defaults (override with environment variables):

| Role | Variable | Default inference profile |
|---|---|---|
| Triage assistant | `TRIAGE_MODEL_ID` | `us.anthropic.claude-haiku-4-5-20251001-v1:0` |
| Judge | `JUDGE_MODEL_ID` | `global.anthropic.claude-opus-4-5-20251101-v1:0` |

Every request and response is logged to `live.log`. Retries use botocore's adaptive mode: up to 8
attempts, with backoff and jitter on throttling. A full live run is 300 triage calls; check Bedrock
pricing before you run it.

Things that behave differently live:
- **Forced tool, not a guaranteed schema.** `toolChoice` makes the model call `record_triage`, but the
  input can still be off-schema; `parse_triage` catches that and the case fails. Some newer models reject
  a forced `toolChoice`; check the model's docs before overriding the model IDs.
- **Sampling.** Triage keeps the model's default sampling, so reruns differ (that is step B3). The judge
  runs at temperature 0, which reduces but does not remove variation.
- **Flaky cases and the gate.** Majority-of-3 is a simplification. A case that passes 60% of the time
  passes a majority of 3 runs only about 65% of the time, so the gate can block a "regression" that is
  just noise. Rerun blocked cases, or average more runs per case, before trusting a block.
- **Small calibration set.** 22 of 25 (88%) has a wide margin; grow the calibration set before relying
  on the judge.
